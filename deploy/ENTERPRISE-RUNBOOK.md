# Business workspace release runbook

This runbook is prepared for Samuel's staging/production operators. It is not evidence that a public release occurred. Read `PRODUCTION-READINESS.md` and resolve its owner-side gates first.

## Stage and provision

Use an isolated Supabase/PostgreSQL staging database first. Keep production data/keys out of developer machines and CI. The personal app's existing schema/users are not migrated automatically.

As the database owner, provision a strong-password LOGIN role named `loamy_enterprise_app`, without superuser, database-creation, role-creation or replication privileges. For a Supabase connection pooler, its username may include the provider's project suffix; the base role must remain `loamy_enterprise_app`.

Review and apply `scripts/sql/enterprise/001_enterprise.sql` as the migration owner. It creates the `enterprise` schema atomically and intentionally fails if that schema already exists. Stop and inspect an unexpected existing schema; do not drop it or rerun a destructive test helper. Record the migration artifact/version. Future releases require separate forward migrations, not edits to an already applied migration.

Runtime connects only as the dedicated application role, using `sslmode=verify-full` and the provider's trusted CA. Keep the schema private and outside the Data API. Verify ordinary browser roles cannot read it. Keep administrative/migration credentials out of the application environment.

For the owner overview/receipt release, apply `002_receipt_extraction.sql` after 001. For an existing 001 installation, back up first and apply only 002; do not regenerate/drop the initial schema. Runtime requires `002_receipt_extraction`. Include both new tables in backup, retention and access reviews.

The release image installs Tesseract (executable plus English data) and Poppler. If packaging without this Dockerfile, install `tesseract-ocr`, `tesseract-ocr-eng` and `poppler-utils` from the OS repository. OCR uses temporary files and fixed subprocess commands; provide writable private `/tmp`, memory/CPU limits and process isolation. No cloud OCR credential or outbound service is required. Extraction accepts up to 2 MB, 20 megapixels for images and three PDF pages. Each external tool has a 20-second timeout; one extraction runs per worker, with ten uncached attempts per user/hour. A failed/unavailable reader leaves manual submission available. Keep OS parser packages updated; test resource limits and representative receipts in staging. Do not add the Docker socket to production: the optional Docker fallback is for guarded local preview only.

## Configure and build

### Reporting and customer-message migration 004

For this release, back up/review and apply `004_reports_notifications.sql` after 003 as migration owner; existing installations apply only missing forward migrations. Runtime requires 004, with 36 private tables. It adds notice drafts, hashed invoice-share capabilities and tracked recurring commitments with restricted updates. The schema generator reproduces 001/003/004 without rewriting applied artifacts or copying preview data. Keep the prior image and verify schema compatibility before rollback; never drop history to reverse the release.

Customer messages remain operator-reviewed. Test partial-payment/overdue candidates, draft text/recipient, changed balances, paid/cancelled exclusions, capture versus SMTP, accepted/failed/uncertain outcomes and one-notice-per-invoice/24-hour limits. The SMTP reservation freezes conflicting allocations/reversals/cancellation for up to 120 seconds; stale sends become uncertain when history is refreshed. Unknown delivery is not automatically retried. Confirm actual recipient arrival and operational investigation procedures in staging; no reminder worker/scheduler is added. Existing SMTP secrets suffice; no direct outbound WhatsApp/SMS provider is configured.

Serve `/customer-invoice` from the same approved HTTPS frontend/API origin. Exercise the public POST token endpoints with an anonymous customer browser: correct invoice/PDF/current totals only, expiry, explicit revocation and cancelled-invoice denial. Other workspace routes still require verified membership. Invoice-link tokens are shown once, hashed in the database and carried in URL fragments/POST bodies. Anyone holding a link can view its invoice/customer details; accept that privacy model explicitly and share only with the intended recipient. Do not log bodies, tokens or full share links in proxies/analytics/error reporters. Revocation cannot recall previously downloaded files.

Runway is an owner-entered cash scenario based on completed-day recorded net burn, not a bank balance or a liquidity guarantee. Confirm observation coverage and transfer classification before relying on it. Test no history, zero/positive cash, no positive burn, per-location scope, debtor balances outside the observation range, evidence-backed recurring candidates and tracked-commitment cancellation. A tracking action neither pays money nor cancels actual supplier billing.

Test ZIP exports with original evidence and without it, on owner and assigned-location finance accounts. Reconcile posted summary totals, visible voids, current balances and supporting-file checksums. Current invoice balances are not historical period-end snapshots. Limits: 366 days, 5,000 ledger records/5,000 scoped invoice balances, 20,000 supporting metadata rows, 1,000 files/25 MiB of originals and one build per worker. Exercise clear oversize/busy failures and browser binary downloads on supported desktop/mobile clients. Configure memory/request timeouts for these bounded in-process reports; larger jobs need a separately reviewed asynchronous export design. Agree downloaded-report retention; protect exports as financial records. Spreadsheet marker escaping is best-effort across clients/re-save workflows; preserve guards and verify against the canonical ledger.

### Supplier/WhatsApp release migration

Apply `003_supplier_whatsapp.sql` after migrations 001 and 002, using the migration owner and a reviewed backup. For an existing 002 database, apply only 003. Runtime now requires `003_supplier_whatsapp`. It adds five private tables: supplier bills/payment allocations and WhatsApp challenges/senders/messages. No prior migration is rewritten. Verify the runtime cannot alter supplier invoice amounts/original evidence and that already retrieved WhatsApp receipt bytes cannot be rewritten. Include all 33 tables in recovery exercises. Do not drop an existing schema to upgrade.

### Connect WhatsApp privately in staging

1. Keep all `LOAMY_WHATSAPP_*` settings unset until ready; the optional integration is disabled by default. Partial configuration fails startup. The local simulation cannot be enabled by a production request.
2. In Samuel's Meta business application, confirm the business phone-number ID, approved ownership/permissions and a supported Graph API version. Store `LOAMY_WHATSAPP_APP_SECRET`, `LOAMY_WHATSAPP_VERIFY_TOKEN` (a distinct random secret), `LOAMY_WHATSAPP_ACCESS_TOKEN` and `LOAMY_WHATSAPP_GRAPH_VERSION` in the secret manager. No token is returned to the frontend. The application version is explicit; this branch does not assume that an old SDK example version is current.
3. Set `LOAMY_WHATSAPP_ROUTES` to a JSON map of each operator-approved numeric phone-number ID to its existing Loamy business ID. This is an operator-managed tenant boundary, not a browser-editable routing choice. Never route one real number to a different business without a reviewed migration of its links/evidence.
4. Set the HTTPS callback to `/enterprise-api/integrations/whatsapp/webhook`, using the matching verification token, and subscribe to incoming message events. This exact callback accepts provider-signed POSTs without a browser Origin; it still requires approved Host/HTTPS/body limits and the app-secret HMAC signature. Other authenticated routes retain Origin/session checks. Test invalid signatures and a retry before enabling real receipts.
5. Run a separately supervised worker using the SAME reviewed image, environment and database: `python scripts/process_whatsapp_inbox.py`. `--once` processes at most one item for a scheduler/rehearsal. It sends no messages. The webhook commits a durable queue before acknowledgment; the worker retrieves media and verifies the hash, actual file type and size. Claims have 180-second leases and survive restart; interrupted claims are retried up to five attempts. Retrieval failures become visible in the staff inbox for explicit retry/manual upload. Supervise restarts and alert on failed/old queued items; a silent stopped worker is not a working integration.
6. Staff signs in with verified email, selects the correct location, opens WhatsApp receipt inbox and creates a one-use code. They send that exact LINK message privately to the operator-confirmed business number within ten minutes. A provider-verified sender is bound to that account/location; display names are never trusted. Send a test receipt after linking, run the worker, open the draft, confirm/extract fields and submit. Verify another reviewer must approve and posting remains explicit. Revocation/removal must stop new intake and queued retrieval.
7. Test real JPEG/PNG/PDF receipts up to 2 MB. No arbitrary download URL is accepted: metadata comes from fixed Graph API; media host is allowlisted `lookaside.fbsbx.com`, HTTPS only, no redirects, streamed size/hash checks and bounded timeouts. If a legitimate future provider changes its media host or sender identifier shape, inspect authoritative fixtures before changing the allowlist/parser. Never loosen it to arbitrary hosts.
8. Group support is **disabled/unverified**. Do not promise capture from existing staff groups; this implementation ignores group-context events. No outbound acknowledgment/template messages, contact-list imports or WhatsApp Web scraping is implemented. Confirm supported private-message payloads against Samuel's actual provider/account, including any sender-identifier changes, before release.

Agree retention for unused link challenges, unsubmitted inbox files/captions/sender identifiers and failed jobs, while preserving submitted evidence/audit links. Restrict logs: do not log raw webhooks, access tokens, download URLs, private phone numbers or receipt contents. The image disables Uvicorn access logs so the handshake query does not expose its verification token; configure proxy/hosting logs to omit/redact callback query strings too. Set body/rate/resource limits and monitor the 30 receipts per staff/hour intake cap (429 means provider retry), worker failures and five-attempt exhaustion. Do not run the legacy personal Gmail scheduler as this worker.

Use `enterprise.env.example` as a list of required settings; populate a secret manager, not a committed file. Configure identical public web/API origins when using the combined container. Configure real SMTP and a test recipient before testing mail. Never set `LOAMY_LOCAL_PREVIEW=1` on this service.

Build `Dockerfile.enterprise` from the reviewed commit. Record the resulting image digest. The container serves the business-only compiled frontend and `/enterprise-api` from one origin. Its runtime dependencies are fixed in `requirements-production.lock`; the original `main.py`/Gmail backend is not packaged or started.

Run as the image's non-root user with a read-only root filesystem, a bounded writable `/tmp`, no added Linux capabilities and `no-new-privileges`. Provide the database CA read-only. No persistent application filesystem volume is needed: canonical records, receipt bytes and issued PDFs live in PostgreSQL.

Terminate public TLS at the approved proxy/load balancer. Limit direct backend access to that proxy and health monitoring. Set `FORWARDED_ALLOW_IPS` to the proxy's exact IP/network, never `*`, so Uvicorn recognizes only trusted forwarded HTTPS/client-address headers. Apply a 3 MB request limit and timeouts at the proxy as well as in the API. Respect the container's concurrency limit when sizing connection-pool capacity.

## Staging acceptance

- `/health/live` returns liveness; `/health/ready` returns readiness only when the database can be read. Responses reveal no database credentials. Wire an alert to readiness failures and server error rates.
- `/business` loads the compiled app. Unknown `/enterprise-api/...` paths return 404, not the SPA HTML. Original personal-app routes are not enabled in the business-only build.
- Plain HTTP to authenticated application paths is rejected once it reaches the API. Host and mutation Origin checks accept only configured origins. A real browser retains an HttpOnly/Secure/SameSite session and cannot use a captured verification link to upgrade a production account.
- Real verification mail arrives, verifies the matching signed-in account and rotates the session. Test a fresh browser, expiration and a replaced link. Confirm the account-recovery/support policy before inviting real users.
- Test separate businesses and every role, revocation, private receipt downloads and financial access boundaries. The database role cannot run DDL, alter issued financial amounts or overwrite audit/receipt history.
- Issue one invoice, retry generation, download its PDF and send exactly one test email with the original attachment. Verify actual recipient arrival and failure/uncertainty handling. Do not confuse provider acceptance with delivery.
- Allocate a partial payment, show the correct outstanding balance, retry, split another payment and attempt simultaneous over-allocation. Verify no duplicate income. Reverse with a reason and recheck cancellation/void guards. Connect real bank/Gmail sources only after account ownership/source uniqueness are established.
- Submit a staff receipt, request clarification, resubmit a new version, reject stale/self review, approve independently and post/link the matching debit once. Category totals must reconcile to the posted ledger and exclude voids.
- Back up and restore the private schema into another staging database. Compare financial rows and receipt/PDF bytes, check application-role permissions and agree recovery targets. Enable the provider's managed backup/retention policy before launch.

## Release and recovery

Obtain owner approval after staging acceptance. Deploy the same tested image digest, configuration and reviewed migration. Begin with a small pilot. No script in this work changes a live alias, deploys publicly or migrates Samuel's database automatically.

Keep the prior application image available. Roll back application traffic to that image when its schema compatibility is established; do not reverse a financial migration by deleting rows or dropping the schema. If rollback would lose compatibility, stop writes and use the reviewed forward-fix/recovery procedure. Restoring a backup requires an owner-approved recovery point and validation before traffic resumes.

The existing SQLite preview is development data only. There is deliberately no script that copies its passwords, sessions, test receipts or fictional bank credits into production.
